# M1.2-relationship-ssot — Make entity relationships a single source of truth

**Status**: Planned. Constituent T3 (`T3-event-sourced-relationships`) drafted; not yet started.
**Sits at**: A focused **sub-milestone of M1** on the sequence axis (`milestone_index` 1.2). Touches one theme: T2-storage (with a forward reference to T2-projection and a future T3 under M3-clean-gate for the drift audit).

**On sub-milestones (Mn.m):** M1 delivered the hand-rolled end-to-end tracker. Dogfooding M1 surfaced focused defects that are *follow-up work arising from M1*, not new capability milestones. Rather than smuggle these into M2-auto-extract (which would bloat M2 and delay correctness fixes), each gets a small, sharply-scoped sub-milestone hanging off M1: **M1.1** (the analyser — currently filed as `M6-analyser`, which should have been M1.1; renumber deferred), **M1.2** (this one — relationship SSOT). The decimal index keeps them ordered between M1 and M2 and signals "M1 hardening, not new scope."

---

## 1. Why this milestone

M1 close-out exposed a single-source-of-truth defect **inside the tracker itself** — the very class of failure T1 §3.1/§3.2 exist to prevent. A plan's parentage (its thematic `t2_parent` and its `milestone`) is read from **four places that can disagree**:

1. the `entity.created` attribute snapshot frozen in the cache (`entities.attributes`);
2. the frontmatter-derived spawn edge `cache-build.py` synthesises **from that frozen snapshot** (`source='frontmatter'`);
3. the **live** `planning/*.md` frontmatter `projection-emit.py` re-reads at projection time in `compute_milestone_progress()`;
4. the `relationship.reattached` event — which is **dead code**: the edge-builder reads `from_entity_id`, but reattach carries `from_parent`/`to_parent`, so every reattach is silently skipped.

Editing a frontmatter field moves source (3) but not (1) or (2); appending a reattach moves nothing. The three representations drift, and there is no first-class, graph-visible way to *move* an entity between parents. This was demonstrated concretely during M1 close-out: re-tagging the mis-filed analyser T3s, and this milestone's own creation, both hit the divergence.

## 2. What M1.2 unlocks

- **One source of truth for relationships.** Parentage becomes a *projection of the event log*. The cache is the only materialised relationship store; `projection-emit.py` reads parentage from the cache, never from live files.
- **A working move primitive.** `relationship.reattached` (extended with an `axis` discriminator: `t2-parent` | `milestone`) becomes live — moving an entity between parents is a real, append-only, graph-visible operation.
- **Frontmatter demoted to a creation seed** (per T1 §3.1): the `entity.created` frontmatter snapshot seeds the first edge; every subsequent move is an event. Frontmatter-vs-event drift becomes *possible-but-detectable* rather than silently authoritative.
- **Proof by re-tag.** The deferred analyser M1→M6 (→M1.1) re-tag and this milestone's own M2→M1.2 correction become clean, event-sourced reattaches that show in the graph.

## 3. How — constituent work

| T3 | Theme | Delivers |
|----|-------|----------|
| `T3-event-sourced-relationships` | T2-storage | Fold relationship edges from the event stream last-write-wins per `(entity, axis)`; add `axis` to `relationship.reattached` (events schema 0.2.0→0.3.0); `cache-build` applies reattach; `projection-emit` reads parentage from the cache; frontmatter demoted to seed. **First acceptance test: the analyser re-tag.** |

This milestone is deliberately single-T3. If more M1-arising relationship fixes appear they fold in here; unrelated M1 follow-ups get their own M1.x.

## 4. Definition of done

M1.2 is complete when:

1. `cache-build.py` materialises a plan's `t2_parent` and `milestone` edges by folding `entity.created` (seed) + `relationship.reattached` (moves) last-write-wins per `(entity, axis)`; reattach is no longer dead code.
2. `projection-emit.py` derives parentage and milestone membership **from the cache**, not from live `planning/*.md` frontmatter.
3. `relationship.reattached` carries a required `axis` ∈ {`t2-parent`, `milestone`} (events schema bumped to 0.3.0; older events remain valid).
4. The analyser milestone is renumbered `M6-analyser` → `M1.1-analyser` and its plans re-tagged onto it via real events — `entity.renamed` for the (completed) milestone plus `relationship.reattached` for the 6 analyser plans (5 phase T3s + the mis-filed `T3-analyser-live-model-catalog`) — with the moves visible in the flow graph and M6-analyser leaving no resurrected/phantom entity (acceptance test; see T3 §3 + D-F).
5. `repack-validate.sh` passes end-to-end; the previously-divergent frozen-`M2` edge for `T3-event-sourced-relationships` resolves to `M1.2` once reattach is applied.

**Out of scope (forward references):** the frontmatter-vs-event *drift audit* is M3-clean-gate work (cleanliness gate).
