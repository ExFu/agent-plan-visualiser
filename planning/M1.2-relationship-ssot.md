## 1. Why this milestone

M1 close-out exposed a single-source-of-truth defect **inside the tracker itself** — the very class of failure T1 §3.1/§3.2 exist to prevent. A plan's milestone membership was read from places that can disagree. `main` fixed the **cache** side: the relationship graph is now event-sourced (a `relationship.reattached` event rewrites the spawn edge last-write-wins; the frontmatter seed comes from frozen `entity.created` attrs, not the live file). What `main` left untouched is the **projection** side:

- `projection-emit.compute_milestone_progress()` still globs `planning/T3-*.md` and reads each file's **live** `milestone:` field.

So membership survives in two representations that can diverge: the **cache fold** (event-sourced, SSOT) and the **`milestone_progress` projection** (live-file read). Edit a `milestone:` field → the projection moves, the cache graph does not; emit a reattach → the cache graph moves, the projection does not. That residual R1↔R3 divergence — now isolated to a single function — is what M1.2 closes.

## 2. What M1.2 unlocks

- **One source of truth for milestone membership.** Membership becomes a *projection of the cache fold* (frozen `entity.created` seed + `relationship.reattached` events). `projection-emit.compute_milestone_progress` reads the cache `relationships` table, never live files. (The *cache* graph was already event-sourced by `main`; this closes the loop on the projection.)
- **A working move primitive — already live on `main`.** `relationship.reattached` rewrites the spawn graph last-write-wins. M1.2 adopts it as-is; **no `axis` discriminator and no schema bump** — `main`'s `(from_parent, child_id)` suppression already disambiguates the two parentage axes (a `T2-*` parent never collides with an `M*` parent).
- **Frontmatter demoted to a creation seed** (per T1 §3.1): the `entity.created` snapshot seeds the first edge; every subsequent move is an event. Frontmatter-vs-event drift becomes *possible-but-detectable* (M3 audit) rather than silently authoritative.
- **Proof by re-tag.** The mis-filed `T3-analyser-live-model-catalog` (`milestone: M1-bootstrap` → `M6-analyser`) becomes a clean event-sourced reattach whose *projection* follows the event — with a frontmatter-edit-alone control proving the file is no longer the mechanism.

## 4. Definition of done

M1.2 is complete when:

1. *(Shipped on `main` — adopted, not re-done.)* `cache-build.py` materialises a plan's `t2_parent`/`milestone` edges by folding `entity.created` (seed) + `relationship.reattached` (moves) last-write-wins; reattach is no longer dead code. Verified post-merge.
2. `projection-emit.compute_milestone_progress()` derives milestone membership **from the cache `relationships` fold**, not from live `planning/*.md` frontmatter. *(This is the delta.)*
3. T2-storage §3.8 is corrected so no methodology prose still claims the frontmatter field is the sole source of truth for membership; it points to the cache fold + the M3 drift audit.
4. The mis-filed `T3-analyser-live-model-catalog` is re-tagged `M1-bootstrap` → `M6-analyser` via a real `relationship.reattached` event; after rebuild it appears under `M6-analyser` in `milestone_progress` **because of the event**, and a frontmatter-edit-alone control is a **no-op** (acceptance test; see T3 §3). `M6-analyser` keeps its grandfathered label and `completed` state — **no rename, no `entity.renamed`, no resurrection**.
5. `repack-validate.sh` passes end-to-end; rebuild is idempotent.

**Out of scope (forward references):** the frontmatter-vs-event *drift audit* is M3-clean-gate work; the M6→M1.1 rename (and the `entity.renamed` migration it would require) is dropped — see the correction below.
